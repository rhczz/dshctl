# dshctl 改动评审

## 概要

评审的产出不是"我看过了"，而是**缺陷 + 位置 + 影响 + 证据**。门禁（格式、`go vet`、测试、覆盖率、三平台构建、依赖与分层）已经能证明的东西不要再复述；评审的价值在门禁证明不了的地方：判据被越界、边界校验被绕开、生命周期没到静止、证据来自自述而不是真实入口。

## 规则

1. **先取真源**：改动涉及的包文档（模型与不变量）、被钉住的测试、README（操作者契约）、`.agents/notes`（为什么与放弃了什么）。取不到就写明缺哪一条，不要用常识代替。
2. **阻塞项与建议分开**，各自按影响排序。风格偏好不写成阻塞项——书写形态有 `dshctl-style` 与 `scripts/check-conventions.py`。
3. **每条发现四要素**：缺陷、位置（文件 + 符号，必要时 `file:line`）、影响（会引发哪个失败模式）、证据（可复现命令与决定性输出，或指向具体测试/包文档段落）。证据不足时写成"待确认 + 需要哪条命令"，不要写成结论。
4. **不重复绿灯门禁**：`make check`/`make ci` 已覆盖的格式化、vet、测试、覆盖率、skip 白名单与三平台矩阵结论不再复述；只报门禁没覆盖、或门禁本身被绕过的部分。
5. **逐条核实或基于技术理由反驳**，不做表演式同意。对"已完成/已修复"的声明要求给出可复现命令，必要时自己重跑，不采信自述。
6. **用真实入口路径取证**：行为类结论跑真实二进制或真实外部工具，而不是只读单元测试的自述。`internal/cli/readonly_test.go` 就是范例——它跑真实二进制断言只读命令零写盘，因为"承诺是关于命令行的"。
7. **核查清单（至少这些）**：
   - 固定 vs 配置是否越界：协议常量、安全不变量被做成 flag/env/配置（Node 下限、进程归属规则、状态目录文件名、`dsh web:` 地址行格式、构建标记路径），或本该随部署变化的写死。
   - 校验是否只在四处边界：CLI 参数、配置文件、状态与日志文件、外部命令输出；操作函数内部不得再有隐藏默认。
   - 生命周期是否到达静止：停/等/清是否真的等到进程树消失，而不是"发出请求即成功"。
   - 结果是否正交上报：超时与退出码、`Unverifiable` 与失败是否各自可达。
   - 资源是否在 teardown 归还：文件句柄、临时目录、日志跟随、子进程、锁。
   - README 与实现是否同步：环境变量、配置键、命令表、退出码。
   - 平台拆分是否被绕过：上层是否出现 `if windows`，平台测试是否只在单平台成立。
   - 断言强度是否足够：新守卫是否被证明会红，或给出 `make mutation` 等价证据。
   - 新增不变量是否带反向用例（会让它变红的输入）。
   - 是否新增依赖、削弱断言、新增 skip、触碰 `bin/` 与 `dist/`。
8. **没有发现就明确说"没有阻塞项"**，并写清覆盖范围（看了哪些文件、跑了哪些命令、哪些没看）。不要为了显得完整而凑条目。

## 触发与边界

- 适用：自查、评审他人改动或 PR、核实"已完成"的声明、CI 变红后判断是不是真缺陷。
- 不适用：通用代码评审方法论走全局 skill；书写形态问题走 `dshctl-style`；门禁怎么跑与 CI 怎么定位走 `dshctl-verify`；生命周期细节走 `dshctl-defensive`。
- 评审只产出结论与证据，不直接改代码；要修就按 `dshctl-tdd` 的顺序（先失败测试）进行。

## 验证

```sh
make check                                              # 可疑时按受影响范围重跑，或 make ci
go test ./internal/<pkg>/ -run <Test> -count=1          # 单点核实
```
