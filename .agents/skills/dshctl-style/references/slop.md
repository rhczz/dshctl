# slop 清单与注释契约

对应 `dshctl-style` 的第 2 条（注释讲契约）与第 13 条（一个事实一个家）。两张表都是"见到就改"的判据，不是写作建议。

## 七种 slop

| 现象 | 为什么是 slop | 怎么改 |
|---|---|---|
| 重复规则 | 同一事实写两处，改一处就产生两个真源，读者不知道该信哪个 | 留一处，另一处改成链接；家的划分见 [AGENTS.md](../../../../AGENTS.md) |
| 历史错层 | 把过程、试错、评审往返写进契约位置（包文档、README、skill） | 过程留给提交信息与 `.agents/notes`；契约位置只留结论、理由与后果 |
| 会腐烂的状态注解 | "目前""暂时""待重构"没有触发条件，也没有人会回来删 | 删掉，或写成 TODO/FIXME/XXX 并写明触发条件（见 `dshctl-style` 第 11 条） |
| 手抄目录 | 手写的文件清单、命令清单、字段清单会与真实结构漂移，且没人会发现 | 改为指向真源：`Makefile`、`--help`、`git ls-files`；实在要列就交给测试钉住 |
| 推理转录 | 把"我先看了 X，然后想到 Y"贴进交付物 | 交付物只写结论与证据；推理留在对话或提交信息里 |
| 段落墙 | 一条规则写成一大段，读者无法逐条核对，也无法引用其中一条 | 一条一行或一条一段，编号或加小标题 |
| 强调通胀 | 通篇加粗等于没有重点，真正的不变量反而被淹没 | 只给阻塞项与不变量加粗，其余靠结构表达 |

## 注释保留什么、删除什么

| 保留 | 删除 |
|---|---|
| 行为与契约：这个函数保证什么、不保证什么 | 代码复述：把下一行 Go 语句翻译成英文 |
| 失败模式：什么情况下返回错误、这个错误对调用方意味着什么 | 测试走查：把某个用例的步骤抄进注释 |
| 时序与并发：谁先谁后、状态在哪个点发布 | 评审历史："按 review 意见改成现在这样" |
| 归属：这个进程/文件/记录是谁的、凭什么判定 | 推理过程："先试了 A 不行，于是换成 B" |
| 后果与非显而易见的取向：为什么不用更直观的写法 | 待办口号："以后优化" |

本仓库现成的范例：`internal/state` 的包文档用一段话给出规则、理由与两类文件的区别——运行记录只由 dshctl 读写，所以非普通文件是残留要清除而不是跟随；配置文件属于操作者，允许放在 symlink 后面。这既是契约，也是"为什么两种文件规则不同"的答案。
