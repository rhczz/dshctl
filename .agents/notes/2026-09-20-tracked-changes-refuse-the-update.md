# 决策: 有已跟踪修改就拒绝切换版本

状态: 已实施

## 问题

`update`/`rollback` 会替换工作区里被跟踪的文件。如果操作者在 checkout 里改了
`pnpm-lock.yaml` 或某个源文件，`git checkout` 要么失败、要么把修改带进新版本
（构建出一个谁也没部署过的混合版本）。与此同时，checkout 里常常有操作者自己的
未跟踪内容——下游插件目录、笔记——这些必须原样保留，否则"回退"会变成一次数据
丢失。

## 决定

- 切换前检查 `git status --porcelain --untracked-files=no`：非空（未暂存、已暂存、
  已删除都算）→ 拒绝，退出码 4，提示先处理，并说明未跟踪文件不受影响。
- 未跟踪文件完全忽略，也完全不动。
- 不提供 `--force`。操作者要放弃修改就自己执行 `git -C <repo> checkout -- .`；
  工具不做"帮你丢掉工作"这种不可逆的事。
- 检查失败（"无法探测"）按拒绝处理，绝不当作干净。
- git 仍是最后防线：即使 dshctl 的检查被绕过，`git checkout` 自己会拒绝覆盖被
  跟踪的修改，以及被上游新增文件挡住的未跟踪文件——这两条都有测试钉住。

## 备选方案

**交给 git 判断。** 改动最小，但 `git checkout` 在修改与目标不冲突时会静默地把
修改带过去，构建结果与任何提交都不对应；这正是"绝不默默降级"要避免的形态。

**提供 `--force` 逃生口。** 对 `pnpm install` 改写 lockfile 这类漂移更宽容，但
多一个危险开关，而且它的语义（丢哪些修改？暂存的呢？）需要操作者完全理解。
拒绝 + 明确的处理提示把选择权留在操作者手里，工具不替他决定。

**对 `pnpm-lock.yaml` 特判。** 把"允许丢弃的修改"白名单化，规则会随包管理器行为
漂移，且下一次安装又可能写回。不引入特例。

## 后果

- 换来：切换永远不会丢操作者的工作；混合版本不可能出现。
- 代价：pnpm 改写 lockfile（版本与生成者不一致时会发生）之后，下一次更新会被拦
  住，直到操作者手动清理；错误信息里给了命令。
- 已知缺口：未跟踪文件与目标提交新增的同名文件冲突时由 git 拒绝，错误来自 git
  而不是 dshctl，但不会被吞掉。

## 验证

- `internal/repo/release_test.go`：未暂存/已暂存/已删除都算脏；未跟踪不算；
  `checkout --detach` 拒绝覆盖已跟踪修改与未跟踪文件，且 HEAD 不动。
- `internal/app/update_test.go`：脏工作区拒绝时服务不停、不切换、不构建。
- `scripts/mutation-check.py`：`a worktree with tracked changes is switched
  anyway`。
