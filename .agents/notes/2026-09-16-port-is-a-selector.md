# 决策: 端口是选择器，不是安装的身份

状态: 已实施

## 问题

一个状态目录本来就能管多个服务：运行记录按端口分开（`dsh-web-<端口>.state.json`），
README 也写着「同一个状态目录可以管理多个端口」。但 `status`、`stop`、`restart`、
`url` 只读**配置里那一个**端口，于是同一台机器上：

```sh
dshctl --port 3081 start     # 记录 dsh-web-3081.state.json
dshctl start                 # 配置里的 3080，记录 dsh-web-3080.state.json
dshctl stop                  # 只停 3080
dshctl status                # “未运行”，但 3081 还在服务
```

3081 上的服务仍在监听、仍在烧 CPU、仍持有 checkout，而 dshctl 里已经没有任何命令
会提到它：`status` 说没运行，`stop` 说没运行，`build`/`update` 只在替换产物时把它
当成一个障碍来报错。要停它只能靠 `--port 3081` 恰好被想起来——这不是「能管理多个
实例」，这是「每个实例都要求操作者记住它」。

根因不是缺失功能，而是模型选错了：把**配置里的端口**当成了「这个安装的服务」。
配置是每次调用重新解析的，它决定 `start` 该在哪个端口启动，却决定不了「已经启动了
哪些」。

## 决定

端口是**选择器**，安装是状态目录：

- `--port`（或 `DSH_PORT`）出现在命令行/环境里 = 操作者点名了一个实例，`status`、
  `stop`、`restart`、`url` 只作用于它。
- 没有点名时，这些命令作用于本状态目录**记着运行记录**的每一个实例，配置端口永远
  排在第一位、其余按端口升序：`status` 报告全部（配置端口在标准输出上排第一，其余
  打在标准错误上，各带自己的 `访问:` 地址），`stop` 停止全部，`restart` 重启所有正在
  运行的，`url` 每个运行中的实例一行。顺序不是装饰：每条命令都从列表头部读「这条
  命令说的是哪个实例」，所以列表一旦被整体按端口排序，退出码和标准输出就会变成
  回答端口号最小的那一个——配置端口恰好最大的机器上才会暴露。
- 发现实例只靠读 dshctl 自己的记录文件，不扫端口、不猜进程：匹配不到记录的服务
  永远不会被当成自己的。
- 跨实例的操作只拿**一把**锁（`stickyLock`），中途不让别的命令插进来；`restart`
  在停任何服务之前先检查所有端口，有一个端口归属不明就整体拒绝。
- `start`、`build`、`update` 不变：`start` 仍然只启动配置里的那个端口（已在运行时
  拒绝启动第二个），`build`/`update` 仍然作用于配置里的 checkout，并在替换产物前
  检查所有端口。
- `status --json` 顶层是配置端口那一个实例（`state`/`url`/`port` 等键不变），新增
  `ports` 数组列出全部实例（配置端口第一，其余按端口升序）；退出码仍然只回答配置
  端口那个问题（运行中 0，否则 3）。多实例的说明只打在标准错误上，标准输出仍是那
  一个实例的报告，脚本不必改。
- `url` 打印每个运行中实例的地址（不点名时全部）；只要打印了地址就退出 0，
  一个都没有才退出 3——管道靠这条约定区分“有服务”和“没服务”。
  `status` 的退出码仍然只回答配置端口那一个问题。
- `stop` 在所有实例都停完或无事可做时为 0；有实例因归属不明被跳过时为 4。

## 备选方案

**保持现状，只把「另一个端口也在运行」打印出来。** 只读命令报全量、`stop` 仍只停
配置端口。它更保守，但没解决报告的问题：操作者仍然要自己把端口抄进 `--port`，
漏一次就留下一个没人管的服务。孤儿是这次事故的形态，不是它的副产品。

**给 `stop`/`restart` 加 `--all`，默认行为不变。** 语义最清楚，但默认仍然会留下
孤儿——而默认路径正是出问题的那条。多一个必须记住的开关，只是把「记住端口」换成
「记住 `--all`」。

**`stop` 默认停全部，`restart` 默认只重启配置端口。** 停是幂等的，重启不是：
把「没点名的 restart」理解成「全重启」会让一次手滑重启整台机器上的服务。最终两个
命令用同一条规则（不点名 = 全部），因为「restart 只重启在运行的那些」已经把风险
限制在本来就活着的服务上，而两个命令行为不一致更难记。

**扫端口来发现实例。** 不采用：dshctl 的归属判断只来自运行记录（包文档不变量 1），
扫出来的监听者没有记录可依，只会变成「猜这是不是我的」。记录文件是 dshctl 自己写
的、按端口命名的，读取它既准确又不需要探测。

**让配置文件记住多个端口（`ports: [3080, 3081]`）。** 不采用：配置文件是操作者
的所有物，运行记录是运行事实。把「现在有哪些实例」写进配置会让 `stop` 之后留下
需要清理的配置残渣，也会让「配置里写了但没启动」和「启动了但配置没写」两种状态
同时存在。

## 后果

- 换来：`status` 再也说不出「未运行」而其实有服务在跑；不点名的 `stop` 是「停掉
  这台机器上 dshctl 启动的全部服务」，`restart` 是「把活着的都重启一遍」。
- 代价：不点名的命令作用面变大了。约束它的是归属判断（只碰运行记录里、启动时间
  吻合的进程）和「只读自己的记录、不扫端口」，所以不会碰到别人的进程；但
  `dshctl stop` 现在可能停掉不止一个服务，这一点写进了 README 与命令帮助。
- 代价：多实例操作拿一把锁，停多个服务时耗时更长，锁超时的可能性随之上升。
- 「漏掉一个实例」只按**运行记录**算：不点名的 `stop` 在有记录、而记录的进程无法
  确认（或记录与端口上的进程对不上）时以退出码 4 结束；端口上只是别人的程序、
  本状态目录从没在那里启动过服务时不算漏。区别在于「这次操作要管的东西还在不在」，
  而不是「这个端口归谁」——把陌生占用也算成漏，会让每台跑着 nginx 的机器上
  `dshctl stop` 都以 4 结束。
- 已知缺口：端口上没有 dshctl 记录的服务（比如手工 `dsh node ... web` 起的）依然
  只被报告为 port-foreign，这一点没有改变，也不打算改变。

## 验证

- `internal/kernel/multi_test.go`：发现、`--port` 收窄、停全部、混合（死记录 /
  陌生监听者）、拒绝重启、地址列表、探测失败不降级成结论。
- `internal/cli/multiport_test.go`：真实二进制的报告序列（`--port` 起一个、
  默认起一个、点名停一个、不点名停剩下的），并断言 `status` 两个端口都报、
  `url` 两个 token 都拿得到、结束后不留记录。
- `internal/cli/twoport_test.go`：原有的两端口回归测试（不互相孤儿化）。
- `internal/kernel/multi_test.go` 的 `TestMovingTheFixturePortMovesItsRecordStore`：
  夹具换端口后必须读写同一个记录文件。这条守的是**夹具自己**：`New` 用
  `Settings.StateFile()` 建记录仓库，夹具曾经在构造时把它定死，于是换过端口的夹具
  读到的是没有任何命令写过的文件——一个只跑单个测试才通过的缺陷。
- `internal/config` 的 W12 (`TestRepodirWriteBackMatrix/W12`)：回写判断用的是
  **设置解析时**的主目录，而不是回写时环境里的那个。设置现在带着 `Home`；
  在两次解析之间换了 HOME 的进程不会因此把「文档只是重复猜测」误判成「操作者做了
  决定」而静默跳过回写。
- 反向证据：把 `config.Settings.StateSelection` 的发现分支改成只返回配置端口后，
  上面这些测试全部变红（已执行，见提交说明）。
